# 1С, обновление поставщика, GIT и ИИ

Это статья о практике обновления измененных конфигураций 1С новыми поставками от вендора с применением GIT и о применении ИИ для этого.
Речь идет именно об использовании GIT совместно с конфигуратором, не про EDT.

## Аннотация

В статье рассматривается подход к обновлению модифицированных конфигураций 1С на основе выгрузки конфигурации в файловую структуру, использования Git для ведения истории изменений и применения инструментов искусственного интеллекта на этапах анализа, автоматизации и разрешения конфликтов слияния.

Цель работы состоит в обосновании практической применимости такого подхода как альтернативы традиционному обновлению через конфигуратор, особенно в условиях значительного расхождения между доработанной конфигурацией и актуальными релизами поставщика.

Метод основан на построении раздельных веток для поставщика и доработанной версии, последовательном переносе релизов в ветке поставщика и выполнении git merge в ветку разработки с последующей автоматической и полуавтоматической обработкой конфликтов. На материале реального проекта обновления УНФ, отстававшей от поставщика на 16 релизов, показано, что сочетание Git, вспомогательных скриптов, простых тестов и LLM-инструментов позволяет сократить трудоемкость работ, повысить воспроизводимость процесса и упростить локализацию ошибок.

Отдельно показана роль ИИ в анализе кодовой базы, генерации служебных скриптов, подготовке тестов и восстановлении поврежденной логики после неудачных изменений. Делается вывод, что в современных условиях использование Git при обновлении конфигураций 1С становится не только допустимой, но и предпочтительной практикой при наличии сценариев автоматизации и поддержки со стороны ИИ.

Ключевые слова: 1С, обновление конфигурации, Git, слияние изменений, merge conflicts, автоматизация, LLM, искусственный интеллект, тестирование.

## Суть

Кратко метод заключается в том, что работа происходит с выгрузкой конфигурации 1С в файлы, а эта выгрузка индексируется в GIT. Создается две ветки, вендора - `type` и измененной конфигурации `dev`. Названия условные, можно как угодно. Первый коммит в `type` исходная версия поставщика, второй коммит в `type` обновленная версия поставщика. Даллее в ветку поставщика От первого коммита создать ветку `dev`, в нее выгрузить доработанную версию. Получаем структуру, которая аналогична той что в конфигураторе. Не помню как точно, вроде "Старая конфигурация поставщика, Новая конфигурация поставщика, Основная конфигурация".
Потом выполняется команда `git merge type`, и все что может объединиться объединяется. Для остального надо разрешить конфликты в ручную или скриптами или ИИ. Про ИИ возможно, скорее всего да, но сам, увы, не попробовал. ИИ мне чинил то, что я вручную поломал, думаю он и с мерджем справился бы за несколько итераций.
Далее это можно продолжать по мере появления новых версий поставщика - добавить новый коммит в ветку типовых, мердж с веткой разработки.

На схеме ниже что примерно должно получиться в репозитарии:

```mermaid
flowchart
    subgraph vendors["type"]
        direction BT
        ИсходнаяВерсияВендора --> ОбновленнаяВерсияВендора
        ОбновленнаяВерсияВендора --> ОбновленнаяВерсияВендора`+1`
        ОбновленнаяВерсияВендора`+1` --> `...`
        `...` --> ОбновленнаяВерсияВендора`n`
    end
    subgraph dev["dev"]
        direction BT
        ДоработаннаяВерсия --> ДоработаннаяВерсияСОбновлением
        ДоработаннаяВерсияСОбновлением --> МногоНашихДоработок
        МногоНашихДоработок --> ОченьДоработаннаяКонфигурацияСОбновлением`n`
    end
    ИсходнаяВерсияВендора --> ДоработаннаяВерсия
    ОбновленнаяВерсияВендора -->|"git merge type"| ДоработаннаяВерсияСОбновлением
    ОбновленнаяВерсияВендора`n` -->|"git merge type"| ОченьДоработаннаяКонфигурацияСОбновлением`n`
  
```

Эту схему можно исполнить как при ведении разработки в GIT, так и собрав такую структуру временно, только под обновление.

### Плюсы и минусы в сравнении с обновлением через конфигуратор

- `+++` Использование ИИ для помощи в обновлении. С конфигуратором ИИ не работает;
- `+` GIT репозитарий в состоянии MERGE может существовать бесконечно долго. Если закрыть конфигуратор или окно объединения все результаты будут потеряны. В конфигураторе, конечно, есть функция сохранять настройки объединения в файл, но это морока;
- `+` Для обработки кодовой базы можно применять скрипты. ИИ здесь как рыба в воде, напишет все что
попросишь. А в конфигураторе скриптов нет, только биоробот мышка кликать.
- `+` Объединение измененных ролей. В конфигураторе нельзя сравнить роли. В git в xml все видно. Типовые роли менять не надо! За это в ад, водить мусоровоз до конца времен. Но бывает.
- `-` Часть конфликтов будет в файлах `.xml`. Для их ручного исправления надо наработать навык, сначала будет много косяков. Впрочем, это то, что ИИ исправляет хорошо;
- `-` Слияние макетов табличных документов практически не возможно, продраться через тучу тегов в XML макета тяжело.
- `-` Программы сравнения не умеют сравнивать код 1С по процедурам. Конфигуратор умеет, если использовать встроенный редактор;
- `-` Придется снять конфигурацию с поддержки. Особенно если это репозитарий с живой разработкой, а не созданный конкретно под обновление. GIT не любит большие бинарные файлы, а поддержка включает в себя полный `.cf` конфигурации поставщика. Кроме того это отрицательно влияет на выгрузку и загрузку конфигурации в файлы, чисто из-за лишнего объема перекачиваемых файлов. Восстановить поддержку потом можно, но с нюансами. Тему с поддержкой в GIT надо расписывать отдельно.
- `-` git merge часто дает иногда ложные конфликты. Особенно в файлах справки. Решается скриптами.
- `-` при изменении версии платформы или режима совместимости ветка `type` может протухнуть, т.к. количество конфликтов будет просто зашкаливать, из-за изменения структуры файлов выгрузки. Эту ветку надо быть готовым в любой момент пересоздать.
- `-` После загрузки файлов из конфигурации на некоторых версиях можно словить баг, когда конфигуратор при сравнении с конфигурацией поставщика будет показывать что почти все формы изменены, хотя по факту там все нормально. Вот здесь описание этого бага для EDT [https://github.com/1C-Company/1c-edt-issues/issues/1531](https://github.com/1C-Company/1c-edt-issues/issues/1531), но на конфигураторе можно тоже самое словить, я знаю. Но у этого есть и плюс - придется таки научиться обновлять через GIT.
- `-` при загрузке обновленных файлов конфигурации, будут странные ошибки, про которые ничего нет в интернете. Это не критично, GIT всегда может откатить файлы к исходному состоянию. И оказалось что ИИ вполне успешно решает такие ошибки.

## Кейс

УНФ, не обновлялась с 2019 года, отставание от вендора 16 релизов. Изменения в конфигурации, в двух расширениях и в куче печатных форм. Сделана кустарная локализация для РБ. Судя по комментам, доработки делали специалисты из трех франчей. Квалификация специалистов разная.

Кто-то при обновлении наделал в модулях моржей, все модули в тегах MRG. После чего накатил еще пару релизов частично, без поддержки. Т.е. было даже не понятно, какая на самом деле там версия поставщика.

Моржей я вычистил и определил базовый релиз за пару дней. ИИ это сделал бы за пару часов наверное, но тогда я не умел.

Перечень изменений и их цель нигде не были зафиксированы, сотрудники помнили далеко не все. Поэтому почти все узнавал от пользователей, когда ломал. Документировал, писал тесты, рефакторил. Плакал о загубленной карме.

В плюсе было только то, что использовался минимум функционала, фактически только CRM, выписка документов и некоторые отчеты. Это позволило пропустить полное обновление через 16 релизов, и обойтись тремя. А подсказал мне это ИИ. При починке одного из обработчиков обновлений, стало понятно, что обработчики версии 3.0.12 допускают обновление с 1.6.25. До нее было два релиза, и третий на 3.0.12. Т.к. функционала использовался минимум, я попросил проанализировать, есть ли удаляемые реквизиты в используемых объектах, ИИ таких не нашел. И я рискнул обновиться сразу через 12 релизов, и получилось. Если бы не получилось, попросил бы исследовать подробнее, через какие можно. Это везение, что разработчики УНФ так сделали.

В общем случае так делать не надо, лучше обновляться по рекомендованной 1С цепочке релизов. И готовить код под множество итераций обновления. В конце концов, после приведения конфигурации к крайнему релизу, рано или поздно выйде очередной.

На ИИ в этом проекте сначала не полагался, у меня был план плотно заняться им после завершения. Поэтому многое делал руками, сейчас бы уже отдал это ИИ и сэкономил бы наверное недели две, а то и месяц.

Началась эта история в ноябре, закончил в начале апреля. Основная часть работы это рефакторинг и добыча из пользователей информации что, где и зачем. Само обновление наверное неделю чистого времени заняло.

## Подготовка кода к обновлению

Это на самом деле самая большая часть работы. Если обновления надо делать регулярно, или обновлять несколько релизов, то качество доработок в плане пригодности к обновлению становиться критичным. Если обновление разовое тогда можно эту часть сократить. 

Кроме общеизвестных подходов, облегчающих обновление, при обновлении через GIT надо стремиться чтобы при выполнении `git merge` количество конфликтов было минимально, а те конфликты что есть, разрешались бы с минимальными усилиями.

Это можно делать в цикле: `git merge` —> посмотреть что не так —> `git merge --abort` —> поправить —> снова `git merge`. Так по кругу, до достижения удовлетворительного результата. Понятное дело, что для ИИ поправить/отрефакторить основное занятие.

## GIT MERGE

Итак, выполнили `git merge`, что-то объединилось само, что-то осталось в конфликтах.
Тут ИИ сильно помог. Во первых, я попроси ИИ провести исследование, какие есть стратегии мерджа GIT и какая из них даст наименьшее количество конфликтов. Победила команда `git merge -Xignore-space-change`.

И попросил написать скрипт, который автоматически разрешает конфликты, правила для которых понятны:[vendor-resolve-conflicts.sh](docs/vendor-resolve-conflicts.sh)

- Все что удалил и добавил вендор разрешать как `theirs`;
- Все что попало в конфликты, и где нет маркера-префикса изменений `яя_`, разрешать как `theirs`;
- Все файлы, которые в проекте принято не менять, разрешать как `theirs`. Туда идут файлы справки, картинки, макеты, формы, роли, подсистемы и т.п.;
- Макеты драйверов торгового оборудования разрешать как `ours`. Я их с помощью ИИ заменил на пустые zip-архивы, чтобы размер `cf` срезать и в git мусор не хранить;
- Все наши объекты с префиксом `яя_` разрешать как `ours`

Ну и так далее. В результате работы скрипта остаются файлы, которые требуют ручного слияния, но их сильно меньше. Конфлиты я разрешал с помощью `WinMerge`, но тут каждый использует что угодно, программ трехстороннего сравнения множество. Некоторые можно в конфигураторе посмотреть, `Сервис —> Параметры —> Сравнение/Объединение`.

Далее наверное на это можно было натравить ИИ, и он бы сам все поправил. Сейчас я в этом уверен, но тогда не был, и делал все вручную. Уверен сейчас потому, что я накосячил, а ИИ мне все ошибки поправил, я ему просто кидал тексты ошибок. И появились статьи, где люди сливали измененные модули 1С просто в чате, и вполне успешно. Так что с документацией, харнесом и GIT вероятность успеха ИИ очень велика.

А вот собирал скрипты и нашел еще такой: [fix-case-merge.sh](docs/fix-case-merge.sh). Это решение проблемы измерений регистров в имени файлов в git на Windows. Надо было бы это тоже в минусы git по сравнению с конфигуратором, но там и так много. Распугаю людей совсем.

Суть в том, что иногда в 1С переименовывают объект, исправляют строчные буквы на прописные. 1С это все равно, а вот git на винде начинает трекать оба файла. `абыр` и `Абыр` для него это разное. `git merge` перестает работать. Есть вроде настройка `git config core.ignorecase false`, но как-то она мне не помогла, может что-то не так делал. Попросил ИИ эту проблему решить, он написал скрипт чтобы это вылечить, сам разобрался в чем косяк, сам написал. Скрипт разовый, просто как пример где ИИ помогает.

## Исправления ошибок после слияния

Это одно из самых тяжелых мест в обновлении через GIT. Оно состоит из двух частей:

- Загрузить измененные файлы в конфигурацию - при этом часто бывают "странные" ошибки, в основном из-за некорректного слияния xml-файлов;
- Ошибки прикладного кода, после того как конфигурация запустилась.

К моему удивлению, ИИ радикально помог при исправлении ошибок загрузки конфигурации. Раньше приходилось разгадывать проблему по мутным описанием ошибок, иногда даже перезапускать слияние каких-то файлов, обычно Configuration.xml
В этот раз я был в плохой форме, разбираться не хотелось и не было сил. Я поступил как вайбкодер, просто кинул описание ошибки из окна в чат и попросил исправить. За три итерации CLAUDE привел Configuration.xml в порядок, все загрузилось. Тут есть особенность, ошибки при загрузке конфигурации надо кидать по одной, а не все скопом. Часто бывает что после исправления верхней ошибки, остальная простыня при следующей попытке загрузи пропадает.

На втором этапе ошибки прикладного кода тоже легко исправлялись ИИ, просто делал промпт такого плана:

```
После слияния с конфигурацией поставщика, коммит [хешКоммита], перестала работать [ФунцияX]. Ниже лог ошибки. Исправь.
```

В том числе была за пол-часа исправлена функциональность формы заимствованного документа. Документ.КоммерческоеПредожение когда-то был форкнут от Документ.ЗаказПокупателя, и далее его функционал развивался отдельно. После прыжка на 12 версий там все стало неработоспособно. Модуль документа и модуль менеджера я поправил сам быстро, а форму пришлось бы сидеть несколько дней. ИИ сделал за пол часа. Там не все работает, но форма открывается без ошибок, а неработающий функционал правиться за один промпт.

```
Документ.КоммерческоеПредожение скопирован из Документ.ЗаказПокупателя. После слияния с конфигурацией поставщика, коммит [хешКоммита], ФормаДокумента не работает из-за изменения структуры конфигурации. Исправь форму по аналогии с изменениями в Документ.ЗаказПокупателя.ФормаДокумента с учетом наших доработок.
```

## Тестирование

Если обновлять одну и ту же конфигурацию несколько раз, тесты будут очень полезны. Потому что в измененных конфигурациях почти всегда есть гнилые места, которые обязательно будут пропущены. Нашел такое - написал тест, при следующей итерации спокоен

Тесты писать жутко скучно. Но это пока ИИ не было. Без ИИ не писал бы. 
Тесты предельно примитивные, без фреймворков. Каждый тест это процедура, которая что-то проверяет. Если проверка не проходит, процедура вызывает исключение. Если проходит - ничего не делает. Процедура самодостаточна, можно использовать без инфраструктуры, просто вызвать.

Для задач по доработке в основном использовал Gemini и Sonnet. Разницы в качестве не заметил. Времени разбираться не было, надо было пилить обновление, а модели вполне норм работали без MCP и я забил. Соннет не ошибается в синтаксисе 1С. Gemini почти не ошибается. Для поиска по кодовой базе GREP вполне устраивает, особенно после того как документация наросла. Стараюсь при постановке задачи писать точные названия конкретных объектов и методов, чтобы оптимизировать поиск.

Не хватало только MCP для анализа данных из 1С. Для решения вопросов типа: заполнен ли этот реквизит в актуальных документах и справочниках? Поленился внедрить, ходил в консоль запросов писать руками. Если бы сделал, конечно удалось бы снести еще много дохлых реквизитов.

## Семантическая суммаризация при коммите

Коммит я выполняю командой [git-summarize-and-commit.md](docs/git-summarize-and-commit.md), которая смотрит изменения перед коммитом, делает файл с суммаризацией этих изменений и включает его в тот же коммит. Это сделано из следующих соображений:

- ИИ при просмотре коммита сможет понять, что там было изменено в этом коммите;
- Я по этим файлам собираю отчеты, когда руководство запрашивает "Что было сделано за период с и по?";
- Не надо писать commit message руками;
- Если ленился делать коммиты после каждого изменения, и накопилась куча изменений, суммаризация позволит понять что там было;

В последнем случае можно написать:

```
/git-summarize-and-commit.md, но раздели изменения по логически связанным частям и сделай несколько коммитов
```

Это единственная команда, с помощью которой ИИ разрешено делать коммиты. В документации у меня явный запрет на коммиты, только вручную делаю, или этой командой.

Это не относиться к обновлению конфигурации, но все-таки практика работы с GIT.

## Заключение

У обновления через GIT и обновления через конфигуратор есть плюсы и минусы, и до 2026 года я бы не сказал какой способ лучше, хотя сам я давно предпочитаю GIT. На сегодняшний день ИИ все поменял. Если использовать ЛЛМ, однозначно надо переходить на GIT. Сравнение в конфигураторе с ИИ не совместимо совсем, а GIT ИИ знает очень хорошо.
ИИ дает возможность легко делать скрипты для автоматизации, и получает буст от доступа к истории кода. Это перевешивает все минусы способа и более высокий порог входа. Надо выучить GIТ, надо не бояться смотреть в XML. Хотя это уже должно быть базой, даже для одинэсников. Как таблица умножения и уметь писать. Третий класс, второй семестр.
